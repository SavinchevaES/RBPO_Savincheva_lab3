# Волонтёрская помощь

REST API для организации волонтёрских акций. Координатор создаёт акцию и задачи, волонтёры откликаются на задачи, координатор допускает их, после участия подаются отчёты, а акция завершается с итоговыми часами по волонтёрам.

**Технологии:** Java 17, Spring Boot, Spring Data JPA, PostgreSQL.

## Сущности

| Сущность | Что хранит |
|---|---|
| Пользователь (`/api/users`) | имя, e-mail (уникальный) |
| Акция помощи (`/api/volunteer-campaigns`) | название, даты, координатор (пользователь), статус |
| Задача акции (`/api/volunteer-tasks`) | акция, сколько нужно участников, начало, длительность в часах |
| Отклик волонтёра (`/api/volunteer-responses`) | задача, волонтёр (пользователь), статус допуска |
| Отчёт об участии (`/api/participation-reports`) | отклик, фактические часы, статус подтверждения |

**Связи:** у акции один координатор, у акции много задач, на задачу откликаются много волонтёров, по каждому отклику может быть один отчёт.

**Статусы:**

- акция: `PLANNED` → `ACTIVE` → `COMPLETED` (есть также `CANCELLED`)
- отклик: `PENDING` → `APPROVED` или `REJECTED`
- отчёт: `PENDING` → `CONFIRMED` (есть также `REJECTED`)

**Правила, которые гарантирует база данных:** e-mail уникален, волонтёр откликается на задачу только один раз, на отклик один отчёт, дата окончания акции не раньше начала, в задаче минимум 1 участник и 1 час, часы в отчёте не отрицательные. Внешние ключи не допускают ссылок на несуществующие объекты, а при удалении акции, задачи, отклика или пользователя зависимые объекты удаляются каскадом.

Для каждой сущности есть CRUD: `GET` список, `GET` по id, `POST`, `PATCH`, `DELETE`.

## Бизнес-операции

Если условия не выполнены, API отвечает `409`.

| Операция | Запрос | Когда можно |
|---|---|---|
| Запустить акцию | `POST /api/volunteer-campaigns/{id}/activate` | акция `PLANNED`, в ней есть хотя бы одна задача |
| Откликнуться на задачу | `POST /api/volunteer-tasks/{id}/apply` (тело: `volunteerId`) | акция `ACTIVE`, задача ещё не началась, волонтёр не координатор акции и ещё не откликался |
| Допустить волонтёра | `POST /api/volunteer-responses/{id}/approve` | отклик `PENDING`, акция `ACTIVE`, на задаче остались свободные места |
| Подать отчёт | `POST /api/volunteer-responses/{id}/report` (тело: `actualHours`) | отклик `APPROVED`, акция `ACTIVE`, отчёта ещё нет, часы не больше длительности задачи |
| Завершить акцию | `POST /api/volunteer-campaigns/{id}/complete` | акция `ACTIVE`, у каждого допущенного волонтёра есть отчёт; необработанные отклики отклоняются, отчёты подтверждаются, в ответе часы по волонтёрам |

Целостность обеспечивается транзакциями (`@Transactional`), проверкой состояния перед изменением и блокировкой строки задачи или акции на время операции (два одновременных допуска не займут одно место).

## Структура проекта

```
controller/   приём запросов, коды ответов, формирование ответов
service/      бизнес-логика и проверки состояния
repository/   интерфейсы Spring Data JPA
entity/       JPA-сущности и enum статусов
dto/          запросы и ответы API
config/       тестовые данные
```

## Запуск

1. В pgAdmin выполнить `db/setup.sql`: создаётся база `volunteer_db` и пользователь `volunteer_app` с правами только на чтение и запись данных.
2. Скопировать `.env.example` в `.env` и вписать пароль (файл `.env` в репозиторий не попадает).
3. Запустить приложение. Таблицы создаются автоматически, при пустой базе добавляются тестовые данные.
4. Один раз выполнить `db/constraints.sql` в pgAdmin под `postgres` в базе `volunteer_db`.
5. По желанию: выполнить `db/permissions.sql` (таблицами владеет администратор, приложению остаётся только работа с данными) и в `application.yml` поменять `ddl-auto: update` на `ddl-auto: validate`.

Приложение работает на `http://localhost:8080`.

## Проверка

Импортировать `postman/volunteer.postman_collection.json` в Postman и запустить коллекцию целиком (Run collection). Она создаёт данные, проверяет CRUD по каждой сущности, выполняет все бизнес-операции (успешные и отклонённые сценарии) и в конце удаляет созданное.
